Luck System Analysis

Client-side Luck module · SparkMod framework · critical · score 122

What is this module?

This is the client-side Luck module for the SparkMod framework. It manages a "Luck" system — a multiplier or modifier that affects how good your drops and rewards are. The module is marked critical (score 122) by the harvester, indicating it is frequently invoked during gameplay.

Architecture at a glance

The system uses a channel + modifier model. Luck is broken into named channels (e.g. "egg", "spray", "plant") — each channel has its own luck value. Individual modifiers stack on top of channels from different sources (pets, gamepasses, events, etc.).

Key design facts

  • This file is client-side only — it mirrors server state but never writes to it
  • Default luck value is 1 (no bonus) when no channel value exists
  • Luck values are cached locally after the first server fetch
  • The server pushes live updates to clients via remote events
  • The Init() function short-circuits on the server — purely a client concern
  • No server-side Luck script was found in the archive — it lives elsewhere on the server

How luck data moves between server and client

SERVER  Luck service holds truth — computes effective luck per channel per player, applies modifiers (pets, gamepasses, events)
↕
REMOTES (SparkMod.Luck.*)

InvokeServer — GetEffective(channel), ListModifiers(channel), ListChannels()
OnClient — ChannelChanged, ModifierApplied, ModifierRemoved
↓
CLIENT (this script)  Caches values in local tables t (channels) and t2 (modifiers). Updates UI signals when server pushes changes.
↓
OTHER CLIENT MODULES  Call GetEffective(channel) or GetEffectiveAsync(channel) to read current luck before rolling drops
Important: The client cache is lazy — on first ask for a channel it hasn't seen, it invokes the server. Subsequent reads are instant from the local cache. The server proactively pushes changes so the cache stays fresh without polling.

Exported functions

GetEffective(_, channel)
sync Returns cached luck multiplier for a channel, or 1 if unknown. Fast — never yields. Used when a cached value is acceptable.
GetEffectiveAsync(_, channel)
async / yields Waits for module to be Ready, then returns cached value. Falls back to InvokeServer if the channel hasn't been fetched yet. Caches result for future calls.
GetModifiers(_, channel?)
sync Returns list of modifier objects for a specific channel, or all modifiers across all channels if no argument. Each modifier has a .channel and .source field.
ListModifiersAsync(_, channel?)
async / yields Fetches modifier list from server, merges into local cache, then returns them. Refreshes the t2 table each call.
GetChannels(_)
sync Returns cached channel list (v3), or empty table if not fetched yet.
ListChannelsAsync(_)
async / yields Returns cached channels if available; otherwise invokes server to get them. Result is cached permanently (channels don't change mid-session).
Init(_)
one-shot Initialises Remotes, registers all three OnClient listeners, fires the Ready signal. Runs only once (guarded by v1). Server skips everything after Remotes:Init().

Signal events — what other scripts can listen to

Ready
Fires once when the module has finished initialising. Async functions wait on this before proceeding. Other scripts can also wait on it.
ChannelChanged
Fires when the server pushes a new luck value for a channel. Passes (channelName, newValue). UI components listen to this to refresh luck displays.
ModifierApplied
Fires when a new modifier is added to a channel (e.g. equipping a luck pet, joining an event). Passes the modifier object: {channel, source, ...}.
ModifierRemoved
Fires when a modifier is removed (e.g. unequipping a pet, event ends). Passes (channelName, sourceName). The modifier is cleared from the local cache.
These signals allow UI and other game systems to reactively update when luck changes — the luck bar on screen, indicator icons, or re-rolling display odds — without polling every frame.

What luck actually does for players

Luck is a per-channel multiplier. Different drop systems query different channels — e.g. egg hatching might read the "egg" channel, gear shop restocking the "gear" channel. A value of 1 = no bonus. A value of 2 = double luck.

Sources of luck modifiers

  • Pets — equipped pets add modifiers to specific channels by source name
  • Gamepasses — permanent luck boost to one or more channels
  • Events — temporary modifiers applied server-side during events like Plant Rush
  • Items / Gear — possibly fertilizer or sprays that grant a temporary luck boost

What this means for drop rates

Every probability calculated so far (eggs, Boss Box, Cosmic Spray etc.) assumes luck = 1. If the server applies a 2× luck modifier to the "gear" channel, Cosmic Spray's effective chance would double. The channel model means egg luck and gear luck are independent — a pet boosting egg luck doesn't help spray drops.

Why no server script is visible

The archive only captured ReplicatedStorage scripts (client-accessible). The server-side Luck handler lives in ServerScriptService and was not harvested — that's where the actual multiplier computation and modifier management happens. This client module is purely a read-only mirror.
